# Clean Code Shit 2.0 Rust core design

Clean Code Shit will use one Rust engine for scanning, sizing, planning and cleanup. A native CLI will ship for Windows, macOS and Linux. The first desktop app will use Tauri 2 and call the same engine.

## Workspace and compatibility

| Path | Responsibility |
| --- | --- |
| `Cargo.toml` | Virtual workspace at the repository root. Rust 2024 edition, resolver 3, MSRV 1.85 and a committed `Cargo.lock`. |
| `crates/ccs-core` | Catalog, operating system adapters, probe, plan, execution, cancellation and audit records. No terminal or UI dependencies. |
| `crates/cleancodeshit` | CLI flags, interactive prompts, terminal rendering and exit codes. |
| `apps/desktop` | Future Tauri 2 workspace member. The app runs `ccs-core` on a worker thread and adapts its events for the webview. |
| `cleancodeshit` and `site/` | The Bash executable remains the 1.x release during migration. The site continues to ship independently and displays the active release. |

Validate the locked workspace with the MSRV on every PR. Use a pinned stable toolchain for release builds and update the MSRV explicitly when dependencies require it. Target Windows 11, macOS 14 and newer, and Linux 5.15 and newer. Validate the oldest supported versions before making those promises in release notes. x86_64 and ARM64 are supported on all three. [Rust 2024](https://doc.rust-lang.org/edition-guide/rust-2024/index.html) · [Cargo MSRV](https://doc.rust-lang.org/cargo/reference/rust-version.html) · [Rust targets](https://doc.rust-lang.org/rustc/platform-support.html)

## Core API and data

Use a **synchronous core**. Scans and tool invocations are blocking operations. The CLI and desktop app can run them off their main thread, subscribe to progress, and share the same cancellation path. The API does not require an async runtime.

| Operation | Contract |
| --- | --- |
| `catalog(platform)` | Yields stable item IDs, groups, risks, labels, action descriptions, target rules, supported platforms and citations. Includes reasons for unavailable items. |
| `probe(request, events, cancel)` | Resolves paths and command endpoints, then returns an immutable scan snapshot. Each item has a status, logical size, optional allocated size, detail rows, warnings and protected identity evidence for planning. A scan can stream partial totals while items are still running. |
| `plan(snapshot, selection)` | Resolves IDs and presets against that snapshot. Returns a read-only plan with actions, counts, estimates, explicit confirmations and blocked items. A stale or incomplete probe cannot authorize a destructive action. |
| `execute(plan, confirmation, events, cancel)` | Revalidates every approved target and action. Returns per-item completed, skipped, failed or cancelled outcomes, plus measured results where available. Completed operations remain recorded if later items fail or are cancelled. |
| Dry run | Returns and renders the plan without starting cleanup commands, creating run logs or writing to a target. Probe commands must pass the fixture checks for read-only behaviour. |

Emit typed events for run start, item start, bounded size snapshots, item completion, action start, partial failures and the terminal result. Give every event a run and item ID where applicable. The CLI renders the same model the desktop uses. The cancellation token is shared by scan workers and child supervisors. A cancelled probe cannot be converted to an executable plan.

Write execution logs as versioned JSON Lines to a private per-user state directory inside the approved home. Use restricted permissions, exclusive creation and the same path checks as cleanup. Record the item, action, timing, timeout or cancellation cause, exit status and capped diagnostics. Redact configured credentials and avoid recording transcript contents. Size estimates are distinct from measured change in available disk space.

## Desktop app (Tauri 2) and the Linux gate

Run the synchronous core on a Rust worker thread. The Tauri adapter coalesces progress snapshots into ordered batches of typed events and sends them to the webview through a Tauri channel. Deliver result, error and cancellation events reliably. The cancel action signals the same token used by scan workers and child-process supervision. Keep Tauri types and IPC out of `ccs-core` so a different UI can call the same API. [Tauri channels](https://v2.tauri.app/develop/calling-frontend/#channels)

The Linux release gate uses installed release builds in both X11 and Wayland sessions, including NVIDIA hardware on both. Replay a 10,000-entry scan while scrolling the item list, then measure the flush vortex using the same fixture and interaction steps. At 60 Hz, require p95 frame time below 16.7 ms during scan and scrolling and during the vortex, in each session. Check that reduced motion replaces the vortex with an immediate result and that a simple rendering mode keeps the list, confirmation and progress usable without the canvas. [Tauri Linux graphics](https://tauri.app/develop/debug/linux-graphics/)

If Tauri misses the Linux gate and a pinned GPUI build passes the same installed-build, hardware, timing and fallback checks, use GPUI on Linux. Consider moving Windows and macOS only after qualifying their builds separately. If neither Linux build passes, defer the Linux desktop release. The shared core and CLI remain independent of the desktop toolkit. [GPUI documentation](https://docs.rs/gpui/latest/gpui/) · [GPUI source and examples](https://github.com/zed-industries/zed/tree/main/crates/gpui)

### Shared catalog

Maintain one schema-versioned TOML catalog in `crates/ccs-core/catalog/items.toml`. Each entry defines `id`, `group`, `risk`, `label`, `action_id`, platform-specific roots and overrides, `must_close`, and official source URLs. Use typed root keys and action enums interpreted by Rust. Catalog data cannot provide shell snippets or change the home boundary. Use `OsString` and `PathBuf` for actual paths.

Generate the public item reference and the site's static item data from that catalog. Preserve a same-origin JavaScript asset for the landing page and verify the generated projection in site CI. Keep the 1.x site check against Bash registrations until the Rust catalog becomes the release source. The demo's fictional sizes and chip aliases remain presentation data that refer to stable item IDs.

## Safety and target identity

1. **Approve one physical home.** Resolve the current principal's home and operating system roots once. Open the home directory and keep its filesystem and file identity. Treat configuration, case variations, relative components and discovered paths as inputs to validate. Reject drive-relative paths, UNC/device namespaces, alternate data streams, and traversal components before opening a Windows target. Reject overrides outside the approved home. Cleanup never admits an arbitrary path from a selection or a discovered filename. [Windows path rules](https://learn.microsoft.com/en-us/windows/win32/fileio/naming-a-file)
2. **Refuse elevated scans and cleanup.** Check real and effective UID on Unix. On Windows query token elevation and enabled Administrators membership. Permit a normal UAC limited token, and refuse full, effective Administrator and system tokens. Help and version output require no filesystem access and remain available. Items needing administrator privileges are unavailable. [Token membership](https://learn.microsoft.com/en-us/windows/win32/api/securitybaseapi/nf-securitybaseapi-checktokenmembership) · [Elevation types](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ne-winnt-token_elevation_type)
3. **Bind actions to the plan.** Capture the item, approved options, root identity and endpoint in the plan. Reopen and verify these, the selected leaf and its relevant parent chain before execution. Block a changed or unverifiable item and require a rescan. Internal delete operations are limited to the catalog allowlist and never use wildcard recursive removal. Block competing runs for the same home with an exclusive state lock.
4. **Keep confirmation in the core.** `safe` and `all` contain no danger or stale items. `--in` exposes stale items without selecting them. Apply `--yes` to non-danger plans only and reject a mixed danger plan before performing any item. For danger, accept exact lowercase `yes` from an interactive terminal or an equivalent typed desktop prompt tied to the specific plan. A piped answer is not interactive consent.
5. **Detect active tools and overlapping data.** Recheck processes immediately before mutation. Compare Windows process image identity and start time using Toolhelp and limited query handles. Use Restart Manager for exact files when a catalog action has an in-use check. Treat inability to verify a required app, a sharing violation, or an incomplete directory listing as unavailable. Never close applications on the user's behalf. [Toolhelp snapshots](https://learn.microsoft.com/en-us/windows/win32/api/tlhelp32/nf-tlhelp32-createtoolhelp32snapshot) · [Query process image](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-queryfullprocessimagenamew) · [Restart Manager resources](https://learn.microsoft.com/en-us/windows/win32/api/restartmanager/nf-restartmanager-rmregisterresources)

### Filesystem adapters

- **Linux.** Use `rustix` descriptor-relative opens. Open chains beneath the pinned root with `openat2`, no symlinks and no mount crossings, including bind mounts. Use descriptor-relative enumeration and removal with no-follow opens and identity rechecks. Reject roots whose parent chain cannot be verified. [rustix filesystem APIs](https://docs.rs/rustix/latest/rustix/fs/index.html) · [Linux openat2](https://man7.org/linux/man-pages/man2/openat2.2.html)
- **macOS.** Use `openat` one component at a time with no-follow flags. Verify filesystem identity on the descriptors and reject mount crossings, including cases where device ID alone is ambiguous. Use `unlinkat` against the verified parent and stop on changed identities. The Unix adapters avoid following replaced links, but path-name removal cannot atomically compare a leaf identity and unlink it. Exclude shared writable roots and require race fixtures before release. A process already acting as the same user remains outside the threat model. [POSIX openat](https://pubs.opengroup.org/onlinepubs/9799919799/functions/open.html) · [POSIX unlinkat](https://pubs.opengroup.org/onlinepubs/9799919799/functions/unlink.html)
- **Windows.** Use `windows-sys` in a narrow platform adapter. Open a single child relative to its pinned parent with `NtCreateFile` and `FILE_OPEN_REPARSE_POINT`, and hold directory traversal handles without delete sharing during the operation. Enumerate the open directory and verify the volume and file ID on actual opened handles. Reserve string path resolution for diagnostics. Skip all reparse points and recall-on-access entries, including junctions, volume mounts, symlinks and cloud placeholders. Do not hydrate cloud files to measure them. Delete by verified handle and treat a sharing violation as in use. Validate directory disposition on NTFS in the first spike. If an adapter cannot delete a directory safely by handle, leave that action disabled rather than fall back to a path-based recursive delete. [NtCreateFile](https://learn.microsoft.com/en-us/windows/win32/api/winternl/nf-winternl-ntcreatefile) · [Handle information](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-getfileinformationbyhandleex) · [Reparse points](https://learn.microsoft.com/en-us/windows/win32/fileio/reparse-points) · [Handle disposition](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-setfileinformationbyhandle)

## Scanning and performance

Use the same **guarded native walker** for probe and action preflight. Implement filesystem identity and directory opens with `rustix` and `windows-sys`, and use `crossbeam-channel` for bounded worker queues. The scanner must consult the active parent handle before descending, enforce OS-specific mount rules and classify Windows reparse tags. `dua-core` offers a useful read-only benchmark comparison, but its entry predicate is not our authority for opening or deleting a target. [rustix](https://docs.rs/rustix/latest/rustix/) · [windows-sys](https://docs.rs/windows-sys/latest/windows_sys/) · [Bounded channels](https://docs.rs/crossbeam-channel/latest/crossbeam_channel/fn.bounded.html) · [dua-core walk API](https://docs.rs/dua-core/latest/dua_core/fn.walk.html)

Use a bounded coordinator queue of verified directory work and at most eight workers by default, with a lower cap when there are fewer CPUs or a device is slow. Workers keep a depth-first local cursor when there is no queue capacity, so they can keep making progress without all waiting for a free slot. Bound open handles and depth. Aggregate counters, capped diagnostics and a bounded list of detail rows per item. Coalesce progress to a snapshot at most every 100 ms and give terminal events a separate reliable delivery path. Stop scheduling on cancellation and join workers after active filesystem calls return. A stalled device can delay that join and is reported as such.

Track logical bytes and allocated bytes separately. Use file length for logical bytes, Unix block counts where available and Windows handle allocation queries only where supported. Leave allocated size unknown when not measured. Sparse files, hard links and APFS clones can make these figures differ from freed disk space. Do not promise to reclaim a hard link's blocks, and do not trade an unbounded inode set for an exact global deduplication claim. [Unix metadata](https://doc.rust-lang.org/std/os/unix/fs/trait.MetadataExt.html) · [Windows allocation and compression information](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-getfileinformationbyhandleex)

### Initial performance gates

On a documented local NVMe reference machine for each OS, use a deterministic 50 GB fixture with about 100,000 files and a separate one-million-entry fixture. The timings are targets to validate before release.

| Measurement | Gate |
| --- | --- |
| 50 GB tree, warm, logical sizing | p95 at most 15 seconds. |
| One million entries, warm | p95 at most 60 seconds and peak incremental RSS at most 150 MiB. |
| First progress snapshot on a local tree | p95 at most 250 ms. |
| Cancellation on a responsive local disk | p95 at most one second to stop and join. |

Report p50 and p95 across at least 20 warm samples after warm-up, with filesystem, host, device and worker count recorded. Report cold results separately using a documented reboot or lab cache-reset procedure where supported. Compare allocated and logical sizes against known fixture manifests with separate sparse, linked and mounted cases. Do not gate PRs on noisy shared-runner wall time. Run bench gates on the reference hosts for release candidates.

## External tool execution

Use a typed argv builder for `npm`, `uv`, `docker`, `brew`, `pnpm`, `go` and Windows NuGet. Resolve trusted absolute executable paths at probe time and revalidate before launch. Run from a neutral private directory inside the home and use a per-tool allowlist for environment and config. Preserve the specific verified cache and endpoint settings. Refuse project-controlled launch hooks and generic Windows batch execution. Recognize supported Node launchers for npm and pnpm and invoke the verified `node.exe` with the known CLI entry point. Unsupported wrapper layouts remain unavailable until tested. [Rust Command and Windows argument handling](https://doc.rust-lang.org/std/process/struct.Command.html)

- **Unix supervision.** Start each invocation in a new process group. On cancellation or timeout, send `SIGTERM`, allow a short grace interval, then `SIGKILL` the group and reap. A tool that daemonizes into a new session falls outside process-group supervision. Do not use that launch mode. [Rust Unix process groups](https://doc.rust-lang.org/std/os/unix/process/trait.CommandExt.html) · [POSIX kill](https://pubs.opengroup.org/onlinepubs/9799919799/functions/kill.html)
- **Windows supervision.** Create the process suspended, attach it to a Job Object with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, then resume it. Block breakaway. If assignment fails, terminate the suspended process and fail the item. On timeout or cancellation terminate the job and wait for the child. Give process-group and job creation a common supervisor interface. [Windows Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects) · [AssignProcessToJobObject](https://learn.microsoft.com/en-us/windows/win32/api/jobapi2/nf-jobapi2-assignprocesstojobobject)
- **Output and timeout.** Close unused stdin and drain both output pipes concurrently under one monotonic deadline. Keep a bounded tail per stream, with a truncation marker and logged duration and exit cause. Supervise help and discovery commands as well as cleanup. If a timeout leaves an uncertain outcome, record it and do not retry automatically except for the explicit uv policy.
- **uv.** Run `uv cache prune`, never remove uv's cache directly. Keep the default 30-second lock wait limit, `CLEANCODESHIT_UV_LOCK_TIMEOUT`, and one announced retry with `--force` on versions that support it. `--force-uv` or `CLEANCODESHIT_UV_FORCE=1` starts with the announced force policy. A cancelled call or ordinary nonzero exit does not trigger a retry. Record forced attempts in the result and log. [uv prune](https://docs.astral.sh/uv/reference/cli/#uv-cache-prune--force) · [uv force introduction](https://github.com/astral-sh/uv/releases/tag/0.8.24)
- **Docker.** Bind the plan to the exact approved local socket or named pipe plus the daemon identity. Read the context endpoint, remove context and remote/TLS overrides from the child environment, and pass the local endpoint explicitly on every call. Refuse TCP and SSH contexts. Recheck identity before each destructive Docker action and stop on context rotation. Preserve dry run and per-tag selection. [Docker CLI environment and host](https://docs.docker.com/reference/cli/docker/) · [Docker context inspect](https://docs.docker.com/reference/cli/docker/context/inspect/)

## Terminal behaviour

Keep the banner and brand colours in truecolor, 256-colour and basic ANSI modes. Use `#F3F5F8` for standard text, `#FFC83D` for emphasis, `#8E919B` for dim text and `#E5383B` for danger. Render without colour or animated progress in pipes or with `--no-color` or nonempty `NO_COLOR`. Preserve `--ascii` and width-aware banners and tables. On a Windows console enable virtual terminal processing only when supported, and fall back to plain rendering on failure. The CLI owns terminal detection, terminal restoration and prompts. Test Windows ConPTY and ordinary redirected output. An interrupted run restores the cursor and returns 130. [Windows console VT sequences](https://learn.microsoft.com/en-us/windows/console/console-virtual-terminal-sequences) · [NO_COLOR](https://no-color.org/)

## Test matrix and parity contract

Keep `tests/00-safety.bats` through `tests/10-uv-lock.bats` as the Bash behaviour specification. Share fixture intent across implementations and keep the shell suite green while Bash ships. Write named Rust assertions for each case, normalizing terminal escapes and platform-specific paths before comparing observable results. Retain the release and site checks separately. Preserve exit 0 for successful list, dry run or cleanup, 1 for operational failure or refusal, 2 for invalid inputs or an unattended danger selection, and 130 for interruption.

| Lane | Required coverage |
| --- | --- |
| Ubuntu, macOS and Windows x64 or native default on PRs | Locked tests, core and CLI conformance, fixture dry run, regular safety and command shims. Run Rust 1.85 checks as a separate job. Start with `ubuntu-24.04`, `macos-15` and `windows-2025` so updates to `*-latest` are explicit. |
| All six release targets | Build and test on native x86_64 and ARM64. Add `ubuntu-24.04-arm`, `macos-15-intel` and `windows-11-arm` to the main lanes and use matching artifact smoke tests. Do not substitute a cross-compile for execution. |
| Unix safety | Symlink swaps, log path substitution, hard links, non-UTF-8 names, mounts and same-device Linux bind mounts. Exercise privileged mount setup only inside an isolated fixture and run the cleaner as the fixture user. Verify Ctrl+C reaps process-group descendants. |
| Windows safety | In-profile and escaping junctions, links and cloud-placeholder attributes; races that replace parent or child entries; volume boundaries, long paths, case aliases, locked files, and token elevation. Test explicit cancellation and abrupt CLI exit with a shim that spawns a grandchild. Verify that closing the job leaves no descendant. |
| Existing behavioural cases | Selection grammar, exact typed consent, presets, no writes from dry run, session and config preservation, active editors, stale Git protection, changing Docker endpoint and every uv retry and failure path. |

[GitHub-hosted runner labels and administrator privileges](https://docs.github.com/en/actions/reference/runners/github-hosted-runners) · [Windows junctions](https://learn.microsoft.com/en-us/windows/win32/fileio/hard-links-and-junctions)

Give each test a fresh fixture root and assert that every writable path resolves under it. Redirect home, known-folder resolution, per-tool overrides, log location and temp files using injectable adapters in core tests. Never ship an environment switch that bypasses the home or elevation checks. Use sentinels in the fixture outside the approved home to prove confinement. Run Windows end-to-end deletion tests under a disposable standard local account with an isolated profile on the hosted VM, since the runner account itself is an administrator. Test that the original elevated token is refused. Use a native test shim executable on Windows and keep POSIX shims on Unix. Shims record exact arguments, emit canned diagnostics, block, change endpoint identity or spawn children. Tests do not use a real development cache or daemon.

## Release and packaging

Extend the existing **custom tag workflow**. It will validate the tag, Cargo version, changelog and intended site release version, and build from `Cargo.lock`. Keeping this pipeline under repository control lets both Windows architectures use the same signing gate before archives and package-manager manifests are created. It also preserves the release verification and follow-up package jobs that already exist for 1.x. Pin actions and container images. [GitHub workflow permissions](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#permissions)

Use numbered pre-release tags such as `v2.0.0-alpha.1` and `v2.0.0-rc.1` for GitHub-only previews. Validate them against the Cargo version and mark their releases as pre-releases. Publish neither stable site updates nor package-manager updates from preview tags. When a stable `vX.Y.Z` release is published and its assets are verified, feed the package jobs and generate a site manifest update for the existing Pages deployment on `main`. Keep the previous links live until the new assets are downloadable.

| OS | Targets and archives |
| --- | --- |
| Windows | `x86_64-pc-windows-msvc` and `aarch64-pc-windows-msvc`, ZIP archives containing the signed executable. |
| macOS | `x86_64-apple-darwin` and `aarch64-apple-darwin`, architecture-specific ZIP archives containing a signed and notarized executable. |
| Linux | `x86_64-unknown-linux-musl` and `aarch64-unknown-linux-musl`, static binaries in tarballs. Verify static linkage and test on the stated minimum kernel. |

Native CI tests the staged files. Sign before packaging, finish notarization before computing release hashes, and verify signatures, SHA-256 sums and provenance from the downloaded assets. Publish per-asset hashes in `SHA256SUMS` and a machine-readable manifest with platform, architecture, filename and digest. Generate GitHub artifact attestations for the shipped archives. Scope the OIDC and attestation permissions to the attestation job and release write permission to publication. Build and signing jobs receive no package-channel credentials. Upload and re-download assets before publishing the draft, then open downstream package updates from that immutable manifest. [Rust target support](https://doc.rust-lang.org/rustc/platform-support.html) · [GitHub artifact attestations](https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations/use-artifact-attestations)

### Signing and owner credentials

- **Windows.** Use Microsoft Artifact Signing Public Trust with a protected release environment and Azure federated identity if the owner is eligible. Basic is listed at USD 9.99 per month and includes 5,000 signatures. It needs a paid subscription and verified identity in a supported region; individual eligibility is narrower than organization eligibility. If the owner is ineligible, use a CA-backed code-signing certificate with a supported hardware or hosted key, with costs quoted by the provider. Authenticode-sign and timestamp both `.exe` files, then verify each before publishing. Signature verification is a release gate; it does not promise immediate SmartScreen reputation. [Artifact Signing quickstart and eligibility](https://learn.microsoft.com/en-us/azure/artifact-signing/quickstart) · [Microsoft pricing](https://azure.microsoft.com/en-us/pricing/details/artifact-signing/) · [Microsoft SmartScreen reputation](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation)
- **macOS.** Enroll in the Apple Developer Program, listed at USD 99 per year, and obtain a Developer ID Application signing identity. Keep the certificate and key in a protected CI environment with the notarization credentials. Sign with hardened runtime and a secure timestamp, submit the ZIP with `notarytool` and require acceptance. A standalone executable or ZIP cannot carry a stapled ticket. If an offline installer becomes necessary, add a signed PKG with a stapled ticket. [Apple Developer Program](https://developer.apple.com/programs/) · [Apple notarization](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution) · [Apple notarization workflow](https://developer.apple.com/documentation/security/customizing-the-notarization-workflow)

## Migration and version plan

| Phase | Scope and exit gate |
| --- | --- |
| 0. Design | Agree on Windows scope, safety claims, signing path and supported OS floor. No product changes in this phase. |
| 1. Core and Windows preview | Implement the catalog and synchronous API. First prove confined Windows traversal, file and directory deletion, token refusal, Ctrl+C and Job Object assignment on both Windows architectures. Then enable verified items in the native CLI. Publish a clearly marked `2.0.0-alpha` preview only after Windows safety tests, fixture conformance and scan benchmarks pass. |
| 2. macOS and Linux parity | Port the remaining actions and run Rust and Bash against equivalent fixtures. Every Bash item and behaviour case must have a named equivalent or an agreed compatibility change with release notes. Require clean package and OS smoke tests on all six targets. Keep Bash and the live site on 1.x while comparing behaviour. |
| 3. Release candidate | Cut `2.0.0-rc` builds with final signing and package metadata. Require all six native builds and tests, exact hashes and attestations, fresh installs and uninstalls, and the reference performance gates. Confirm release automation and the rollback path from the candidate without publishing a stable update. |
| 4. Stable | Ship `2.0.0` as Rust on all platforms after parity and signing gates. Switch documentation and installer routes to Rust. Freeze the Bash implementation on the 1.x line and retain tagged downloads for rollback and supported legacy systems. Do not maintain a separate Bash lite product. |

## Owner decisions

| Question | Recommendation |
| --- | --- |
| Which operating system versions should receive 2.0 support? | Start with Windows 11, macOS 14 and Linux 5.15. Keep 1.x available to users outside that scope and widen support only with maintained fixture lanes. |
| What signing spend and identity should the project use? | Confirm the publisher's Artifact Signing eligibility and approve the Apple membership. For an ineligible Windows publisher, price a hosted CA alternative before setting a stable date. |
| Which accounts and names should publish packages? | Use `cleancodeshit` and consistent owner-controlled identities. Reserve the WinGet package ID, Scoop bucket and Chocolatey ID early, and reuse the existing tap and AUR setup. |
| Which Windows cache families should be left for a later release? | Ship verified package and agent paths first. Keep Visual Studio component caches, uncertain editor roots and broad temp cleanup deferred. Keep WSL and Docker disk images permanently outside filesystem actions. |
| Should Bash remain a supported alternate engine after parity? | Freeze and archive 1.x with a limited security window. Use the same Rust engine for both CLI and future desktop work. |
